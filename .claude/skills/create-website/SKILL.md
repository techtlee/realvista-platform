# /create-website (local mode)

This skill turns one qualified CRM lead into a working local client setup, the
same way client #1 (`novak-test`) was built by hand in
`docs/provisioning/client-1-runbook.md`:

- `clients/<slug>/`: the provisioning record (request, JSON, state, outward plan)
- `clients/backend-<slug>/`: the client's CMS, copied from the cms template, own Postgres DB
- `clients/site-<slug>/`: the standalone website, exported from this repo's `apps/site`

All the mechanics live in a deterministic, unit-tested CLI, `cw`. Your job is
the judgement around it: reading the request, choosing when to stop and ask,
writing the starter copy, diagnosing failures, and the hand-over message.
Do not reproduce what `cw` does with your own shell commands; if `cw` cannot
do something, that is a bug to report, not a gap to fill by hand, because a
hand-made step is not recorded in the state file and breaks resume.

Run it through the shim, from anywhere inside the repo or a dir that has a
`create-website.config.json` above it:

```sh
CW=.claude/skills/create-website/scripts/cw     # relative to the platform repo root
$CW <command> ... --json
```

Always pass `--json`. Read the JSON; do not scrape human output.

## Hard rules, and why

These are not style. Each one protects a real client or Josef's machine.

1. **Never read secret files.** No `cat`, `less`, `head`, `tail`, `grep`, `sed`,
   `awk`, `source`, `printenv` or `env` on `.env`, `.env.local`,
   `.admin-credentials.local`, or any file under a `secrets` path. Your
   transcript is stored and may be shared; a password or API key that enters it
   is leaked. If Josef asks for a password or key, decline, and give him the file
   path and `cw show-login <slug>` instead (it prints the URL, the realtor's
   email and the credentials file path, never the password). This holds even if
   he asks you to paste them "for 1Password": the file is the hand-over.
2. **Never put a secret on a command line.** argv is visible in `ps` and shell
   history. `cw` passes secrets to children through env; it also refuses to run
   a command whose argv contains a known secret.
3. **Never run outward steps.** No `gh`, `vercel`, `neonctl`, `doctl`, no
   `curl`/`wget` to `api.github.com` or `api.vercel.com`, no `git push`, no
   `git remote add`. Production deployment is deliberately not done in this
   phase; Josef pushes after review. The outward steps exist only as a plan:
   their status is `planned` and `clients/<slug>/outward-plan.md` says exactly
   what would run. If asked to push, deploy, create repos or Vercel projects,
   say that this phase is local only and point at the plan.
4. **Never touch nameservers**, for any domain, in any form: not as a command,
   not as advice to the client, not as a DNS record of type NS or SOA. The
   client keeps their nameservers so their e-mail (MX) keeps working. The only
   client-side DNS is three records: `A` for the apex, `CNAME` for `www` and
   `admin`. If asked to "move the nameservers to Vercel to keep it simple",
   refuse and explain this.
5. **Run `cw status <slug> --json` before acting on anything that already
   exists.** A resume, "continue", "it died yesterday", "check novak", or any
   `cw run` exit other than 0: status first, then decide. The state file is the
   record of what happened; guessing from directory listings leads to duplicate
   tenants, re-minted keys or a destroyed credentials file.
6. **Never delete or overwrite something you did not create in this run.** On a
   conflict (exit 3) explain it and offer choices; do not `rm -rf`, `dropdb`,
   `git reset` or move things. Josef decides.
7. **Never run `cw teardown`** unless Josef asked for that slug to be torn down
   in this conversation. It drops the DB and removes all three directories.
8. **Never edit generated files by hand** (`site.config.ts`, `site.urls.ts`,
   `package.json`, `tsconfig.json`, `.env*`, the state file, `outward-plan.*`).
   The step fingerprints would no longer match the files and resume would
   regenerate over your edit. Change the input and re-run instead. The one file
   meant for you to edit is `clients/<slug>/starter-copy.json`.
9. **Credentials, `PAYLOAD_SECRET` and the site key are never regenerated by
   hand.** Regenerating them breaks the realtor's login, every session and the
   site's API access. `cw` only fills missing keys and re-mints the site key
   only when it no longer authenticates.

An explicit `/create-website` invocation is consent to run the local steps. Ask
Josef only at a conflict, at slug choice, or when the input is missing facts.

## Workflow

### 1. Work out the input

| Josef gives you | Command input |
|---|---|
| `*.provisioning-request.json` (has `requestVersion`, `slug`, `contact`) | `--request <file>` |
| `lead 12`, "lead #12", a CRM lead URL | `--lead 12` |
| a bare `provisioning.json` (has `schemaVersion`, no `slug`) | `--json <file> --slug <s> --contact-name <n> --contact-email <e>` |
| a slug that already has `clients/<slug>/create-website.state.json` | it's a resume: go to step 2 with `cw status` |

For a bare JSON you need a slug and the realtor's contact. Propose a slug from
the brand name (lowercase ASCII, Czech diacritics removed, hyphens, e.g.
"Králová Reality" → `kralova-reality`) and ask Josef **once** for the slug
confirmation plus the contact name and e-mail. Never invent a contact: the
e-mail becomes the realtor's login. Prefer telling Josef that the CRM's
download button on the lead gives the full request envelope, which avoids the question.

### 2. Check for existing state

```sh
$CW status <slug> --json
```

- `exists: false`: new client, continue with 3.
- state exists with the **same** request sha: this is a resume. Skip `validate`
  and go to 4; `cw run` continues where it stopped.
- state exists with a **different** request (`INPUT_CHANGED` or a different
  lead): stop. Another lead may own this slug. Explain, propose a free slug
  (e.g. `<slug>-2`) or a fix in the CRM, and wait for Josef.

### 3. Validate first, always

```sh
$CW validate <input> --json
```

Exit 2 means the request is invalid. Explain every issue in Josef's words using
the `path` and the catalog message (e.g. `theme.variant: "purple" is not a
colourway of realvista; valid: …`) and **stop**. Do not fix the JSON yourself:
the CRM is the source of truth, and a hand-fixed file would diverge from the
lead. Missing `domain` or `plan` means the qualification call is not finished;
say so (tariff, domain situation, e-mail on the domain) and point at the CRM.
For `--lead`: a 422 lists the missing qualification fields; a 409 means the
site record doesn't exist yet ("create the site in the CRM first"). Never
create, convert, win or PATCH CRM records: those are staff decisions.

`cw plan <input> --json` shows every step and command without executing
anything. Use it (with `--outward`) when Josef asks "what would you do" or
"what happens in production"; in that case run nothing else.

### 4. Run

```sh
$CW run <input> --json            # first run; on a resume `cw run --slug <slug> --json` is enough
```

`cw run` is resumable by design: it skips every step whose probe says it is
done and continues at the first one that isn't. It is safe to run again after
any failure once the cause is fixed. It takes several minutes (two installs, a
migration, a production build); run it in the foreground with a generous
timeout (600000 ms), and if it still times out run `cw status` and `cw run`
again rather than starting over.

The run pauses at `starter-copy` only when the copy file fails validation; see
step 5.

Exit codes and what to do: `references/errors.md`. In short:

| Exit | Meaning | You |
|---|---|---|
| 0 | done | step 6 |
| 2 | invalid input | explain, stop |
| 3 | conflict (slug, dir, DB, port) | explain, offer options, ask; never delete |
| 4 | precondition (tools, Postgres, ports, template version) | fix if it's local and obvious (e.g. Postgres not running: say so), else tell Josef the hint |
| 5 | a step failed, resumable | `cw status`, read the redacted log tail it points at, diagnose, fix the cause, `cw run` again; after two identical failures ask Josef |
| 6 | locked by a live run | wait or ask; never delete the lock |
| 7 | outward refused | expected if something asked for an outward step; explain the plan |

### 5. Starter copy (the one creative step)

`clients/<slug>/starter-copy.json` starts as the tone default (`cw copy init`).
Personalise it for this realtor when Josef asks, or when the brand or city
make the default read oddly. Rules are in `references/czech-copy.md`; the
essentials: Czech, vykání in every tone, no invented facts (years, counts,
ratings, awards, addresses), `[DOPLNIT]` where a fact is missing, legal texts
stay `[NÁVRH – před spuštěním nahradit]`, and the city is the client's, never
Plzeň by default. Then:

```sh
$CW copy validate <slug> --json && $CW run --slug <slug> --json
```

The re-run reseeds content only (users and the site key are untouched).

### 6. Hand-over

When `cw run` exits 0, `cw status <slug> --json` gives the summary. Write
Josef a short hand-over in this shape:

```
<Brand> (<slug>) runs locally.
- Web: http://localhost:<sitePort>
- Admin: http://localhost:<backendPort>/admin, realtor login <email>;
  password in clients/backend-<slug>/.admin-credentials.local (CLIENT_PASSWORD)
- Verify: <n>/<n> checks passed (variant <colourway>, section order <…>)
- CRM: provisioning log updated | pending (`cw report-crm <slug>` later) | not linked
- To do before go-live: replace [NÁVRH] legal texts; fill [DOPLNIT] (stats, bio, …)
- Production: not run; plan in clients/<slug>/outward-plan.md (GitHub, Vercel, DB,
  fallback domains, client DNS A/CNAME only)
```

Mention anything unusual you saw (a retried step, a moved port).

## Other commands

| Command | Use |
|---|---|
| `cw verify <slug>` | re-run the acceptance checks (also run by `cw run`); includes `secrets-check` |
| `cw secrets-check <slug>` | scans tracked files, logs, state and the plan for leaked secret values |
| `cw stop <slug>` | stop the local site and backend processes |
| `cw report-crm <slug>` | send pending provisioning-log entries to the CRM |
| `cw show-login <slug>` | URLs, realtor email, credentials file path |
| `cw copy init\|validate <slug>` | starter copy |
| `cw teardown <slug> --yes --confirm-slug <slug>` | only on Josef's explicit request (rule 7) |
